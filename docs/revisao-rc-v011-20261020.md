## REV-01 — P1: backup conflitante pode ser sobrescrito silenciosamente

**Confirmado em reprodução local usando os métodos reais de `CommercialReport`, sem navegador nem backend.**

1. Existe backup com assinatura `r:1`, texto local não enviado e possíveis arquivos locais.
2. A versão remota carregada tem assinatura `r:2`.
3. `restoreBackup` retorna `conflict`, sem instalar um bloqueio de escrita ou arquivar o backup antigo.
4. `flushBackup` continua permitido. Um clique dentro do relatório agenda esse flush, e minimizar o app também o aciona.
5. `backupDraft` recebe os dados remotos e a assinatura nova; o store grava com `put` na mesma chave UID/tipo/visita. O conteúdo conflitante anterior é substituído, incluindo sua lista de arquivos.

Arquivos: `src/ui/commercial-report.js` (`restoreBackup`, `scheduleBackup`, `flushBackup`); `src/services/report-drafts.js` (`save`, chave única e `store.put`). O caminho técnico em `script.js` também avisa sobre conflito sem impedir backups posteriores; identificado estaticamente, não reproduzido dinamicamente nesta revisão.

**Difere do risco antes aceito FUT-DR03/FUT-DATA08:** não é somente ausência de interface para abrir um backup preservado; a preservação em si não se sustenta após o próximo backup. Por isso INF-10 foi reaberto. Não há prova de que isso já aconteceu com um promotor.

**Correção mínima recomendada:** manter o backup conflitante separado ou impedir sua sobrescrita/remoção até resolução explícita. Aplicar aos relatórios comercial, treinamento e técnico. Não exige reescrita do script nem mudança de backend.

## Implementação da correção

- Store mantém arquivos de conflito em chave separada, na mesma transação que remove/substitui o backup ativo. Não há mudança de versão/schema nem requisição Firebase/Worker.
- As três aberturas de relatório informam a assinatura remota ao store. O backup divergente retornado serve para exibir o aviso; sua cópia durável já está arquivada antes de qualquer save/cleanup.
- `loadConflicts(uid, atividadeId, tipo)` permite recuperar registros com texto e Blobs. Não foi criada interface de resolução; FUT-DATA08 continua para evolução. Não remover os dados do site: arquivos continuam locais ao dispositivo/origem.
- Se arquivamento falhar por quota, a transação aborta e mantém o original. Abertura do editor falha explicitamente em vez de prosseguir sem preservar backup.
- Mesmo sem load intermediário, save com baseline divergente arquiva a versão anterior. Backups compatíveis continuam atualizando normalmente. Arquivos de conflito não são apagados automaticamente; política de retenção fica pendente.
- Regressões: três tipos de relatório; novo flush; remoção imediatamente após conflito; reabertura de store; isolamento UID/visita/tipo; múltiplas versões; falha de arquivamento; ciclo real dos métodos `restoreBackup → flushBackup` comercial. Test double com transação/rollback, não navegador real.
- Cache do SW passa de v73 para v74 para distribuir a correção também a quem abriu o Preview anterior.
- Ambiente shell local indisponível nesta sessão. Validação será executada pelo GitHub Actions sem credenciais de produção. Não alegar teste local ou homologação Android desta correção.
